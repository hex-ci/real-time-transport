# 实时交通 PRD

> 定位：**单用户个人通勤出行工具**。

---

## 1. 产品概述与定位

### 1.1 产品定位

回答一个问题：**「还有几分钟来车，后面几班分别多久？」**

不是地图，不是时刻表查询器，不是给路人看的展示大屏。使用者只有一个人，使用方式固定、每天重复。

区别于地图 App 的三点：

1. **不做地理底图**，用纯拓扑呈现车辆与站序的相对关系，1 秒内可读。
2. **不做路线规划**，只服务已经固定的通勤线路（规划在别处完成）。
3. **不替人做决定**，并列给出多班次与步行耗时，由使用者自己判断。

### 1.2 使用场景

需求只服务这四个场景，其他一律不做。

| 场景 | 时刻 | 使用者位置 | 要得到的答案 |
| --- | --- | --- | --- |
| **A 出门前** | 早/晚高峰 | 家门口 / 公司门口 | 还有几分钟来车、后面几班分别多久 |
| **B 接驳中** | 通勤途中 | 步行去站台的路上 | 还赶得上吗 |
| **C 临时查** | 低频 | 任意 | 某个未关注的站台有哪些车 |
| **D 夜间边界** | 末班时段 | 任意 | 今天还有没有车 |

**明确不属于场景**：在车上（通勤固定，知道在哪下车）；给他人看的信息展示。

### 1.3 核心设计原则

1. **纯粹拓扑，拒绝冗余地理底图**：不加载瓦片地图与弯曲路网，完全依托拓扑站点逻辑轴线展现相对空间关系，降低渲染负担与视觉干扰。
2. **折返与直线（RouteBoard）站牌美学**：国内长公交线路动辄 40~60 站，采用经典站牌的多行「折返走线」机制解决窄屏排布痛点，并支持一键切换直线贯通单轴长卷。
3. **极客工业风（Dark-mode First）**：
   - 主基调为深空暗色（`#0B0F19` / `#0F172A`），契合 OLED 节能与高对比度需求。
   - 轨道与站点采用通透呼吸发光光效，数字统一等宽字体（JetBrains Mono / DIN）。
   - 动效即信息：仅在车辆位移推算、到站脉冲、状态变化时触发平滑过渡，严禁无关装饰动效。
4. **打开即结论**：不建推送通道、不建 service worker、不建常驻定时任务。使用者手动打开。

### 1.4 硬约束（不可协商）

1. **零假数据**：上游没给的字段就是 `undefined`，界面显示「暂无 / 未知」。绝不塞兜底值，绝不用编造公式估算。
2. **移动端优先**：所有 UI 改动必须在手机宽度下验证。
3. **WCAG 2.1/2.2 AA**。
4. **高德 Key 不得进入浏览器**：所有高德调用走服务端。高德 Key 是 Web 服务 Key，不是 JS API Key。
5. **数据源名称、技术实现细节不得出现在界面上**。

## 2. 功能需求

### F1 · 当前关注列表（核心）

首页列出关注的线路，每条给出**到上下班站点的剩余分钟 + 后面几班的分钟数**。

**主信息**（第一眼要看到的）：

```
NNN路                   开往 XX公交场站
5 分 · 17 分 · 29 分
```

多班次**并列显示，不压缩成单一结论**。成因是真实使用方式：看一眼发现 5 分钟来不及、或手头有工作，就往后看后续班次，决定 10 分钟还是 20 分钟后出门。

**出行参考**（辅助，弱化显示）：设置了锚点后额外给一行

```
步行 6 分 · 现在走还来得及          /   步行 6 分 · 赶不上这班
```

- 定位是**参考不是替代**：主信息永远是多班次；参考只回答「步行要多久」，最终判断由使用者做
- 不得因为有了参考行就隐藏或压缩班次列表

**参考口径**：设 `walk` = 锚点到站台的真实步行耗时，`eta₁` = 本班车剩余时间，`T` = 站台等待容忍值

- `eta₁ - walk ≤ T` → 现在走
- 否则 → `(eta₁ - walk - T) 分钟后出门`

`T` 可配置，默认 3 分钟。`T` 同时是**安全边际**：设 3 分钟意味着提前 3 分钟到站台，吸收了「车早到」与路上意外的风险。

**边界（必须遵守）**

- **无锚点** → 只显示多班次，不给参考行。不得用任何默认值代替步行耗时
- **无在途车辆** → 按 F3 显示运营状态
- **数据陈旧或降级** → 按 F4 标记来源；参考行不给。基于陈旧数据说「现在走」比不给更危险

### F2 · 通勤起终点锚点

保存「家」和「公司」两个位置，作为 F1 参考行的起点。

- 早高峰用「家」，晚高峰用「公司」（复用 §5.2 的通勤情境 + 早晚方向模型）
- 设置方式：一次性获取当前定位并保存；可清除
- **不做地图拖动选点**：那需要浏览器端 JS API Key，违反硬约束 5

### F3 · 收班与末班表达

明确回答「今天还有没有车」，而不是含糊的「暂无来车」。

三种状态要有不同表达：**运营中** / **末班车已过（附今日末班时刻）** / **首班车之前（附首班时刻）**。依据是 §5.3 的运营日时刻表。

### F4 · 数据可信度标记

使用者能分辨一个数字是**真实车辆位置**算出来的、**本系统推算**出来的，还是**读自发布的时刻表**。

**三态**（与 `packages/shared/src/data-provenance.ts`、`apps/web/src/provenance-copy.ts` 一一对应）：

- **实时**（`live`）：**上游数据本身** —— 真实车辆的读数，或对真实车辆的观测。**本系统自己算出来的值不属于这一档**
- **排班推演**（`schedule_simulation`）：本系统按时刻表 / 行车间隔推演出的值（生成的列车及其报时）
- **精确时刻表**（`exact_timetable`）：已发布的分钟级时刻表本身

**没有来源**（`null`）→ **不渲染任何标记**。「没有来源」与「实时」是两件不同的事，未知绝不向好看的一档取整。

- 必须有文字说明，不能只靠颜色区分（无障碍要求）
- 不得把推演值渲染得和实时值一样

这是硬约束 1 在界面上的落地：内部已经没有假数据了，但使用者看不出来等于没做到。行业成熟做法可参照 Transit 的「脉冲波纹 = 实时 / 灰显 = 按时刻表 / Cancelled」。

### F5 · 站台聚合大屏

- 适用场景：使用者已身处站台，附近有多条线路可选——也是「关注模型之外的兜底」
- 视觉形态：机场/高铁站风格的实时起降时刻表（翻牌动效 / 发光行）
- 信息维度：线路编号、开往方向、倒计时到达（按耗时由小到大排序）、剩余站数、距离、数据来源标记
- **边界**：不做换乘规划

### F6 · 线路拓扑报站屏（RouteBoard 核心视图）

单条线路详情页，用 Konva.js 呈现折返多行与直线贯通两种排布，展示站序、实时车辆位置、目标站。

**这是相对地图 App 的差异化能力**——高德官方 FAQ 明确「PC 端的公交线路详情页主要展示静态信息……不提供公交车实时位置追踪」。本工具正好落在这个空白里。

**折返排布示意**（站名以占位符示意）：

```
[A站] ──●───●───●───[🚌]───◎───┐ (第1行：从左向右)
                                │ (平滑半圆弧 U-Turn)
┌──◎───●───★(目标站)───●───┐    │ (第2行：从右向左)
│ (平滑半圆弧 U-Turn)       │    │
└──●───●───[🚌]───●───●────┴───► [B站] (第3行：从左向右)
```

**布局与几何排布算法**

- **响应式站点疏密计算**：依据屏幕宽度与站名排版间距动态计算单行容纳数量（移动端竖屏每行 4~5 站；桌面宽屏每行 10~12 站，保持工业大屏感）
- 折返模式下：奇数行自左向右，偶数行自右向左，行间以切向平滑的 180° 半圆弧衔接
- 直线模式下：全线沿单一大轴贯通展开，支持拖拽滑行与聚焦定位
- **横屏/宽屏自适应**：横屏与宽屏保持高密度排布，竖屏手机采用大间距疏密自适应

**视觉图层拆分（Konva.js Layering）**

1. **轨道层**：深色冷灰底轨；已过路段暗灰、未过路段电光青蓝发光；折返处渲染圆润 U-Turn 弯道，线宽一致
2. **站点节点层**：普通站点为实心发光圆点，站名排布在轨道外侧；换乘枢纽站为带同心外环的双重圆点并附换乘徽标；离我最近站为金色发光地标 + 外扩水波纹动效；目标下车站为终点旗帜标记 + 强调发光环
3. **列车动态层**：拟物化机车图元；沿线方向自动对齐（直线段保持水平姿态，U-Turn 段随圆弧曲率平滑旋转）；车辆悬浮气泡标注即时速度与车辆代号
4. **视口交互**：多点触控缩放（Pinch-Zoom）与平滑拖拽；「聚焦目标站」浮动按钮，一键缓动居中至离我最近站与前行来车之间

### F7 · 加到主屏

能加到手机主屏，点一下直达结论页，减少「打开」的成本。

Web 做不了小组件 / 锁屏 / Live Activity / 后台到站围栏（全部要求原生能力），「加到主屏」是 Web 能做到的最接近形态。**不加 service worker、不加推送。**

### F8 · 置顶

首页可以把**一条**线路置顶，让它固定在最上面。

- **持久**：置顶后一直在最上面，只有使用者主动取消才解除
- **同时只能一条**：多条置顶等于没有置顶
- **置顶是状态，不是位置**：它叠加在顺序之上，**不重写任何线路的顺序**；取消置顶后那条落回自己在顺序里的位置，不是从头排起（见 F9）
- **只在首页存在**：置顶的入口、标记、取消**全在首页关注列表**，设置页不感知它。这是「当下这一刻我要看这条」的动作 —— 放进设置页就失去意义，它也是临时状态而非配置项
- **卡片必须有标记**：置顶的卡片要有明确标记，否则「它凭什么叫置顶」在用户眼里不是功能而是 bug

### F9 · 关注线路拖动排序

设置页可以拖动调整关注线路的顺序，排完即生效、随时可再调。

- **依据**：现状的顺序就是**添加顺序**，而添加顺序不是想要的顺序
- **全部线路都参与排序**：置顶只是一条优先条件（类似论坛置顶帖），不是把那条从排序里摘出去。**所有线路共享同一份顺序，置顶那条也有自己的位置**
- **排序是两个关键字**：**首页的展示顺序**以 `is_pinned` 为第一关键字、顺序为第二关键字 —— 置顶的排最前，其余按顺序排列；取消置顶后落回它在顺序里的位置（不是从头排起）
- **顺序是位置，置顶是状态**：两者正交。取消置顶不改动任何顺序，置顶也不重写任何顺序
- **设置页显示原始顺序，且完全不含置顶**：它是纯粹的顺序编辑器 —— 置顶那条按它本来的位置待着，**不显示任何置顶标记**。置顶只属于首页（见 F8）
- **移动端用独立拖拽手柄**：整行长按拖动会和滚动、点击进详情打架
- **顺序全局一份，不按城市分开**：列表只有几条时，分城市维护两份顺序只会增加复杂度
- **边界**：只作用于首页关注列表，不影响站台聚合页（/platform）

### F10 · 换乘链路与出门决策

**要解决的问题**：起点站好判断 —— 倒计时就是等车时间，一次比较就够。但一旦有换乘，人就算不出「我出门能不能赶上换乘点那班车」：需要把「步行 → 等第一段 → 坐第一段 → 换乘步行」串起来，而其中最关键的「坐第一段要多久」并不在人的脑子里。这不是人懒，是信息不在手上。

**页面**：独立页面，不是首页的一块 —— 它是与「关注线路列表」不同的功能面。

**链路由使用者录入，不由系统规划**：

- 每条链路 = 「接驳段 + 乘车段」交替，**起点由通勤目的决定**：上班从「家」出发，下班从「公司」出发（见下方边界）
- 乘车段录入：**线路 + 上车站 + 下车站**
- 接驳段**自动计算**：相邻两段的站点都带坐标，用路径服务算步行 / 骑行耗时，不需要手输
- 支持**多条**链路，并按**通勤目的**区分（上班 / 下班），复用现有通勤情境与早晚方向模型
- 首版段数：首尾接驳 + **最多两段乘车**。数据结构按 N 段设计，UI 先只支持两段，以后放开不必改模型

**每一段的时长必须可溯源**（本功能与「零假数据」共存的前提）：

| 段类型 | 时长来源 | 当前状态 |
| --- | --- | --- |
| 地铁段 | 该站真实时刻表（若已载入） | 已载入分钟级官方时刻表的站点走 `StationTimetableService` 覆写，按 F4 标记为**精确时刻表**；其余站点按「每站 135 秒」推演，标记为**排班推演** |
| 公交段 | **实时到站**：同一辆车在下车站的 ETA（车辆有稳定 id，可跨目标站对上） | 能力已具备（`targetOrder` 定向 ETA）。所以「下车时刻」是实时预测，不是静态估算 |
| 接驳段 | 路径服务耗时（按真实距离） | 已缓存（`AmapGisService` 步行 ETA 缓存，TTL 24h） |

→ **不给点结论的判据不是「段数」，而是每一段的来源等级。**

**输出形态：余量带位为主，分钟数同时给**（核心设计）

要「一眼看出来」的那个东西是**余量带位** —— 带位是解读，且对估算误差鲁棒。但**分钟数也必须给**：最终判断要留给使用者（与 F1「不替人做决定」同一条原则）。只有带位没有数字，等于又替人做了一次决定。

- 三带：余量充裕 → 就是这班；余量紧 → 就这几分钟（**1–3 分钟**，即站台等待容忍值，边界含 3）；余量不足 → 实际是下一班
- **诚实降级**：当余量已小于误差量级时，不给单一结论，给两个分支 ——「赶得上就是 A 班，赶不上就是 B 班」
- **分钟数必须标注来源与新鲜度**（F4 + 最后更新时间），且必须来自**同一来源**：不允许「先显示推演值、真数据一到就跳 10 分钟」这类跳变（本项目已踩过这个坑）。避免跳动的办法是保证来源一致并标注新鲜度，**不是把数字藏起来**

**页面与入口**

- **一级入口，与首页并列**。它服务「出门前」这个最高频场景，藏在设置或二级菜单里等于没有
- **首页不露出链路结论**。首页是「关注线路列表」，混进链路结论会让它变成两个功能面的拼接。若日后发现链路页的使用频率超过首页，再考虑提上去

**边界**

- **链路起点由通勤目的决定，不作为录入项**：上班 = 从「家」出发，下班 = 从「公司」出发。这是**定义**而不是偏好 —— 让使用者再选一次，等于允许存下「上班 · 从公司出发」这种自相矛盾的链路。方向与时段是两件事：时段由 F2/F5 的早晚通勤时段承担，与链路起点无关。支持任意地点会稀释「锚点」的边界，而锚点是 F2 的地基；临时用别的地点属于已划到范围外的「临时起点」
- 运行期不做定位（同 F2）
- 接驳方式**可配**（步行 / 骑行），不默认都是步行。本仓库是开源项目，功能不能只对某一个人的情况成立。**粒度是「进入每一段乘车段的那一段接驳」** —— 一条链路里可能一段走路、一段骑车；没选过时按步行计价
- 骑行接驳的时间**不只是骑行耗时**：还要计入找车与停车。做成**可配 + 默认值**（默认加 2 分钟，可按段覆盖）—— 零假数据约束的是**上游数据**，不是**使用者自己的参数**（T 已是同类）
- **由使用者录入，不由系统规划** —— 与 §3 范围外一致：不引入外部路径规划来替使用者选路线

**录入界面（本功能的需求，界面待建）**

「链路由使用者录入」是本功能的定义前提，因此**设置页必须提供链路的录入与编辑入口** —— 它不是可选的增强项：没有它，「链路由使用者录入」就没有落地的地方，这个功能不成立。

- **位置**：**设置页下的 `/settings/chains`** —— 设置索引里的一页，与关注线路、通勤时段、位置锚点并列（见 4.1）。**不新增一级入口** —— 链路页是读结论的地方，不是录入的地方
- **形态**：**逐段录入**（乘车段的三件与本节上文「乘车段录入」同一条）—— 一条链路 = 名字 + 通勤目的（上班 / 下班）+ 若干乘车段（每段可带自己的接驳方式）
- **方向按使用者自己声明的上下班方向标注，并据此排序**：关注行里已经存着 `morningDirection` / `eveningDirection`（在详情页设上下班上车点时记下的），录入界面据此在每个方向选项上标出「上班方向 / 下班方向 / 上班·下班」，**没声明过的不标**，上游的「开往 X」照旧保留。排序只把当前目的对应的那条排到前面（上班目的 → 上班方向在前），未声明时保持原序。**任何方向都不因目的被停用或隐藏** —— 「先往反方向坐到枢纽」是真实走法；系统排序与标注，不替使用者做选择
- **站点从该线路的站序列表里选，不手输站名**：选定的是 `(站名, 站序)` 这一对；站名是给人看的，站序才是定位凭据（线上同名站不止一个，地铁对同一站在上下行的站序也不相同）。契约层看不到站序列表，只能校验这一对自身的一致性，**「这一对确实在站序里」只能在录入时保证**
- **接驳段不录**：相邻两段的站点坐标已经够算步行 / 骑行耗时（同本节上文）
- 服务端 CRUD 已齐备（`GET` / `POST` / `PATCH` / `DELETE /api/transit/commute-chains`），界面接上即可；`seq` 由服务端按数组顺序写入，不由界面给值

**编辑器必须校验的规则**（与 `packages/shared/src/schemas/api.ts` 的 `CommuteChainLegSchema` 同源，同一套判据在录入时就地拦下，不靠提交后报错）

| 规则 | 判据 | 为什么 |
| --- | --- | --- |
| 公交段只能顺行 | 公交（`lineId` 不带 `subway_` 前缀）必须**下车站序 > 上车站序** | 公交上下行是两个不同 lineId，存下来的 lineId 已经定死了方向；下车站序更小就是把方向录反了 |
| 地铁段允许反向 | 地铁（`lineId` 带 `subway_` 前缀）**允许下车站序 < 上车站序** | 地铁两个方向共用一个 lineId，方向由站序先后表达；在录入端禁掉反向，会让合法的反向链路录不进来 |
| 不能同一站 | 上车站序 ≠ 下车站序 | 从一站到它自己不是乘车段 |
| 站名与站序是**一对** | 上车站的站名与站序**同时给出或同时留空**，下车站同理 | 单独一半既定位不到也不是「未选」；未选用 `null`，**不用空字符串**（空串会读成名为「」的站，那是一个不存在的站） |
| 至少一段乘车 | 段数 ≥ 1 | 一段车都没有的链路给不出任何结论（`no-legs`） |
| 站点必须选完才能保存 | 某段的站名 / 站序仍为 `null` 时，保存前提示补全 | 半截的链路存下去，链路页只能回 `station-unset`；录入端能就地解决的问题不留给读端 |

**`transferExtraMinutes`：`null` 不是 `0`**。`null` = 使用者没配，推演层取默认值；`0` = 确实没有额外时间。两者含义不同，界面**不许把未填写渲染成 0**，也不许把已填的 0 悄悄写回成 `null`。

**录入界面不得承诺产品做不到的事**：

- 不提供「自动规划一条链路」或路线推荐 —— 系统不替使用者选路线（见 §3）
- 不在未载入官方时刻表的站点上给分钟级换乘结论，也不把推演值说成实时值（F4，长期方案见 F13）
- 不承诺「录完就能赶上某班车」：班次结论由链路页按各段来源等级给，录入界面只负责把事实录准
- 服务端拒绝时如实报错（`400` 带契约的消息），不静默吞掉、不假装保存成功

**已知精度提升项**：地铁段默认是 135 秒/站 的推演。分钟级官方时刻表覆写机制（`StationTimetableService`）已经落地，能把已载入站点的推演换成真实值；但覆盖数据来自**逐站人工转录官方图片时刻表**，不具普适性 —— 与开源普适性目标相冲突。因此覆写只覆盖已转录的站点，其余站点保持推演；它作为「可贡献的可选增强」存在，不作为普适方案的地基。

覆写数据的**存放方式**是本阶段的过渡形态：全部时刻表现在装在一个 TypeScript 模块里，要覆盖每条线路（至少北京全网）必须另找存储。**搬存储、不动机制**是已确认的后续阶段，见 F13。

### F11 · 手动刷新

点一下立即取上游最新数据重算，不等下一次推送。

- **适用面**：**首页关注列表**与**换乘链路页**都需要
- **解决的是什么**：数据本来就是实时推送的，所以刷新解决的不是「数据陈旧」，而是「**我此刻要一个确定的最新值**」。它同时给使用者一个明确的时间锚点
- **必须分工刷新对象**：
  - 刷新**实时类**数据（到站、车辆位置、链路余量）
  - **不刷新**长 TTL 数据（线路站序、接驳路径耗时）—— 那些不是「更新一下就会变」的东西，重取只是白耗上游配额
- **必须节流**：服务端「多客户端只拉一次」的设计本来就是为了避开上游风控，手动刷新是唯一能绕过它的入口。因此必须有冷却与上限，并给出明确反馈。产品实际使用的文案是 `正在刷新…` / `已刷新` / `刷新太频繁`（冷却时附「N 秒后可刷新」）；刷新失败与连接中断另有各自的文案（`刷新失败 · 未能取到最新数据` / `连接已断开 · 请检查网络`）。刷新请求被服务端拒绝时返回 `429` 与 `Retry-After`
- **必须可见**：显示**最后更新时间**。点了刷新而界面没有可感知的变化，使用者只会认为按钮坏了

**边界**：刷新按钮不是绕过缓存的通用后门，它只作用于实时类数据。

### F12 · 车厢拥挤度

把上游已有的车厢拥挤度如实呈现，让人在多个班次之间权衡时有依据。

**数据来源**：车来了渠道的 `buses[].busTagList[]`。上游标签形如：

```
{"imageUrlKey": "拥挤度_1", "title": "不拥挤", "sort": 5, "dispatch": false}
```

- **等级由 tag 自己的 `title`（上游自己声明的那两个词）判定，按「全串精确相等」匹配**。`title` 不只是给人看的文案：它就是上游声明的等级词。**绝不允许子串 / 前缀 / 后缀 / 正则匹配** —— 历史上用「包含『拥挤』」去匹配，而「不**拥挤**」里含「拥挤」，导致一批实为不拥挤的车被显示成拥挤
- `imageUrlKey`（`拥挤度_N`）**不再是查找依据**：它的域**无界**（实测出现 `拥挤度_5`，而 `_2`/`_4` 从未出现）。实测到的 (key, title) 对写在代码里作为**证据**，不作为查表

**等级映射必须实测确定，不得推断**：

- 实测到的 (key, title) 对，一律取上游自己的原词：`拥挤度_1` = 不拥挤（各采样线路均出现，113 次）、`拥挤度_3` = 拥挤（晚高峰三轮、两条最繁忙线路，30 次）、**`拥挤度_5` = 拥挤（仅 1 路，7 次，其 `title` 与 `_3` 一字不差）**。**界面文案同样取上游实测的 `title` 原词**（「不拥挤」/「拥挤」），不得自造「畅通」「适中」「较拥挤」这类实测中不存在的档位措辞
- `拥挤度_2` / `拥挤度_4` 从未出现，语义**未知**：**未实测到的词**一律 `unknown`，**不许猜成某一档**，也不设「适中」这类未观测的中间档。按 `title` 判定的好处正在这里：今后任何自称「拥挤 / 不拥挤」的等级都会被判对，而没见过的词仍是 `unknown`（诚实）—— 不依赖我们事先枚举过哪些 key

**覆盖范围与缺失表达**：

- 仅公交（车来了渠道）有；**地铁没有实时拥挤度** → 一律 `unknown`
- **不得用时段推断拥挤度**。时刻表能推车在哪，推不出人多不多 —— 地铁引擎不按时段推断，一律 `unknown`
- 数据源降级（apizero 等）无此字段 → `unknown`
- **「无数据」与「不拥挤」在界面上必须可区分**。把「不知道」渲染成「不拥挤」是替使用者做判断，与 F4 同一原则

**呈现位置**：站台聚合页与详情页看板呈现该字段（取值口径见下）；是否在关注列表新增呈现，待定。

**取值口径（已落地）**：

- `chelaile.ts` 的 `parseCongestion` **只匹配 `imageUrlKey`（`拥挤度_N`）**，不匹配 `title` 文案。曾经的 `title.includes('拥挤')` 会把「**不**拥挤」判成 `high`（上游 14 辆车 tag 全为「不拥挤」时接口全返回 `high`），该反转 bug 已修掉；未识别的等级一律 `unknown`
- 映射表只有实测到的两项：`拥挤度_1` → `low`（界面词「不拥挤」）、`拥挤度_3` → `high`（界面词「拥挤」）；`拥挤度_2` / `拥挤度_4` 未实测，一律 `unknown`。契约随之只保留实测档位（`unknown` / `low` / `high`），不预留未观测的中间档。`high` 只表示「实测到的较高一档」，**不表示量表顶端**——将来若实测到更高档，那是新的一档，不得由此反推
- 拥挤度是**独立的展示事实**：行状态与拥挤度标记各自表述各自的事实，不再共用一个兼作它用的字符串字段
- 模拟模式下不得把生成的拥挤度伪装成真实值

**边界**：

- 不引入众包上报（见 §3）
- 拥挤度**不参与任何自动判断**（不做「拥挤就别上」这类结论），只作并列信息供人自行权衡
- 语义未确认的字段（`capacity`、`sort`、`dispatch`）不依赖

### F13 · 地铁精确时刻表迁入数据库（已规划的后续阶段，尚未实施）

**要解决的问题**：F4 的「精确时刻表」一档与 F10 地铁段的精度提升项，都依赖分钟级官方时刻表；而这份数据现在全部装在一个 TypeScript 模块里（`packages/transit-adapter/src/data/subway-timetables.data.ts`）。目标是覆盖**每一条线路（至少北京全部线路）**，体量远超单站 —— 以现有这一份为标尺：**单站**（7 号线群芳）的生成文件已经 753 行 / 约 13.7 KB。按「每站 × 每方向 × 工作日/双休」铺开，源码模块承担不了这个规模：它会随服务端一起编译、被类型检查逐行读取，规模再放大就不是源码该承载的东西。所以**目的地是数据库**，不是更大的 TS 模块。

**现状事实**（计划的前提，均经代码核对）：

- 现有数据是**读官方时刻表图片人工转录**得到的（使用者的方法），`sourceNote` 记着来源；不是接口抓来的
- 该模块头部标着 `AUTO-GENERATED … Do not edit manually`，但生成它的脚本（`knowledge-base scripts/subway_line7_qunfang.py`）**不在本仓库**，已丢失。因此机器上这一份模块是数据的**唯一副本**
- 由此这份模块是一个**过渡形态**：既不许手改（改了就与丢失的生成器脱钩），也不作为长期存储
- 覆写机制本身是好的，且**不动**：`StationTimetableService` 按 `lineId::站名` 建索引，命中即由 `queryStationArrivals` 给出分钟级发车时刻、按 F4 标为**精确时刻表**；未命中返回 `null`，由地铁引擎按行车间隔推演并标**排班推演**

**本阶段的范围：只搬存储与加载，不动机制。** 分钟级覆写、`lineId::站名` 索引、`isExact` 溯源标记、「未覆盖的站点照旧推演」全部保持原样；变的只是数据从哪来、怎么进内存。

**约束（无论怎么存都必须成立）**：

1. **绝不编造时刻表**。某站某方向某日型没有时刻表 → 与今天**完全一致**的行为：`query()` 返回 `null`，该站按引擎推演、标**排班推演**。不许用行车间隔或任何估算「补」出分钟级时刻表来充数
2. **存储遵守仓库既有的迁移规则**：只允许**新增**迁移文件（下一个编号 `008`），不得回头改 `001~007`；迁移按文件名顺序应用，且**必须自带回滚段**（`-- migrate:down`，运行器 `apps/server/src/db/migrate.ts` 对没有回滚段的迁移直接拒绝回滚）
3. **加载路径不得把「没有时刻表」变成「看起来有时刻表的答案」**：加载失败、或按城市查不到任何行，必须表现为**无覆写**；不许表现为「今天没车」，也不许表现为「按某个兜底时刻表发车」。运营日边界（首班前 / 末班后返回空）是既有规则，不能被加载路径改写
4. **迁移只能从现有模块导入，不得重新生成**：生成器已丢失，任何「重新转录 / 重新生成」的路径都是把唯一副本换成一个来源不同的新副本。导入必须是**幂等**的（可重复执行，结果一致）
5. **数据卫生（§11）不因数据是公开交通数据而放宽**：测试夹具与示例不得出现维护者的真实通勤线路组合

**本阶段不解决的事**（避免把它当成「覆盖全网的完成」）：

- 不新增线路数据本身：迁完之后覆写仍然只覆盖已转录的站点，`135 秒/站` 的推演仍是其余站点的默认
- 不解决「逐站人工转录」这条路本身的普适性问题（F10 已记为未决）

**实施计划**：见仓库 `.hermes/plans/` 下名为 `*-subway-timetable-to-database.md` 的计划（本目录已在 `.gitignore` 中，属本仓库的计划存放处）。

## 3. 范围外（明确不做）

| 不做 | 理由 |
| --- | --- |
| 车上 / 下车提醒 | 通勤固定，在哪下车是已知的 |
| 推送 / 锁屏 / Live Activity / 主屏小组件 | 纯 Web 技术不可行；且明确不要主动触达 |
| 外部路径规划（让系统替使用者选路线、生成方案） | 上游规划接口的公交/地铁段只有首末班与静态预估值，没有任何实时字段；且 `time` 参数不校验末班车，无法判断某方案今天还能不能执行。而这类比较所需的输入 F1 已提供。**F10 的换乘链路是使用者自己录入已知路线、不调用外部规划，不在本行范围内** |
| 关注线路的「起步段 / 换乘段」角色标记 | 使用者本人清楚每条线路属于第几段；换乘决策由 F10 的链路页承担，不是给关注线路贴标签 |
| 首页聚合建议（「今天走哪条」） | 跨线路判断由 F1 的并列多班次承载 |
| 众包上报机制（`userName` / `userPhoto` 那套） | 机制前提是「最近 10 分钟内 + 他人确认」，单人工具不成立；实测该字段在响应中为空。**上游已有的拥挤度本身是另一回事，见 F12** |
| 车牌号 | 字段存在（`licence`）但服务端未下发 |
| 路段路况（`roads[].TPC` 路况指数） | 到站时间本就是上游按车辆实时行进给出的预测，已含路况影响；单独展示只是把同一件事换个说法，对决策无净增信息。而「看路况」本质是地图需求，已明确不做 |
| 公交发车**预测**时刻表（车来了 `line!summary` 的 `timetable[]`） | 「隔多久来一班」F1 的实时到站列表已经用**真数据**回答了 —— 相邻班次的时间差就是实际间隔。再叠一层上游的**预测**时刻表，是用更差的来源回答同一个问题。公交首末班已在用 `line.firstTime` / `lastTime`；高德实测也没有发车时刻表（只有首末班） |
| 按通勤时段分别排序 | 列表只有几条时是过度设计；且设置页里不可见的状态切换会造成「改了没生效」的困惑 —— 晚上改的顺序只在晚间列表生效，次日早上看没变化就会认为功能坏了 |
| 临时起点 | 家/公司两个锚点够用 |
| 法定假日班表（节假日日历） | 使用者已定：**不做**。地铁班表只按星期几取工作日/周末表，法定假日（中秋、春节等）会按当天的星期几取表；`调休` 上班日已由星期几规则天然覆盖。这是**具名限制**而非缺陷 —— 被问到时如实说明，不解释成数据错误 |
| 本系统自己算的到站分钟 | 使用者已定：**不做**。实测这类外推的误差**没有固定符号** —— 同一条公式在一条短程密集站线上偏早 5–10 分钟、在一条长环线上偏晚最多 28 分钟，而它会直接喂给「现在还来得及吗」的出门结论。上游不给分钟时，行只报缺位、不给数字，保留它**能**说的事实（还有几站）。 |

## 4. 页面架构

```
[首页 /]                    关注线路卡片流 + 通勤情境条 + 站台聚合入口
   │
   ├── [换乘链路]             通勤链路的出门决策（与首页并列的一级入口，见 F10）
   │                         链路的录入与编辑在设置页，链路页只读结论
   │
   ├── [线路详情 /line/:id]   RouteBoard 折返与直线动态报站屏
   │
   ├── [站台聚合 /platform]   虚拟站台多线起降看板
   │
   └── [设置 /settings]      设置索引：四行，每行给出该域的当前状态（事实，见 4.1）
          ├── [关注线路 /settings/lines]     关注线路增删与拖动排序（F9）
          ├── [通勤时段 /settings/schedule]  早晚高峰起止时刻（存 `user_settings`）
          ├── [位置锚点 /settings/anchors]   家 / 公司（F1 参考行的起点，见 F2）
          └── [通勤链路 /settings/chains]    链路录入与编辑（线路 + 上车站 + 下车站，逐段录入，见 F10）
```

**进入设置的三条路径**（改造后都要成立）：

1. **索引行整行可点** —— 第 N 行到第 N 个域：整行是一个 `<RouterLink>`，不是脚本跳转（`router.push`），这样语义、键盘可达与「在新标签页打开」都是浏览器原生的
2. **深链接** —— 四个子页面都是真实路径：`/settings/lines`、`/settings/schedule`、`/settings/anchors`、`/settings/chains`（规则见 4.1）
3. **应用内已有的指向改到具体那一页**（今天都指向 `/settings`，指向哪一域要看各自的文案）：

   - `views/overview/components/empty-state.vue` ——「去搜索并关注线路」→ `/settings/lines`
   - `views/commute-chain/components/chain-empty-state.vue` ——「去设置起点位置」（`action === 'settings'`，其判据是锚点未保存）→ `/settings/anchors`
   - `views/commute-chain/components/transfer-card.vue` ——「去设置起点位置」（refusal 的 `action === 'settings'`）→ `/settings/anchors`
   - `components/header-nav/main.vue` 的「设置」导航项是**索引**的入口，继续指向 `/settings`
   - F1 与 F10 的「未设置「家」位置 · 在「设置」中设置」是无链接的文案，措辞不改：设置这一层仍叫「设置」（`views/overview/reference-line.ts`、`views/commute-chain/refusal.ts`）

**Layout 约定**：`views/` 下的组件用扁平 `.vue` 文件 + 桶导出，类型放 `views/<域>/types.ts`；全局 `apps/web/src/components/` 用 `kebab-name/{index.ts,main.vue}`。两者写法不同，不要混用。

**SFC 块顺序**：`<script>` → `<template>` → `<style>`。

### 4.1 设置页的页面结构

**改造内容**：把一个 841 行的设置页（`apps/web/src/views/settings/index.vue`，四个域同屏）拆成**一个索引页 + 四个子页面**。这是**纯结构搬移**：同一批控件、同一套行为与数据，只变它们所在的位置。页面树与 URL 见本节上文。

**索引行的摘要只陈述事实**：

- 每行给该域**当前的**状态：关注线路给条数、通勤链路给条数、通勤时段给已保存的时刻（写法沿用折叠态，如 `07:00–10:30 · 17:30–21:30` 这样的**实存值**；**没选过就给「未设置」** —— 无论因为从没存过行，还是存过行但从没选过时段：内置默认值不得显示成使用者自己的配置）、位置锚点给「已设置 / 未设置」
- 摘要里没有建议、没有评价、没有「去配置」这类动作词 —— 动作由行本身的链接承担，摘要只放事实；条数只在列表读到之后给（**读失败与确实为空必须分得开**：`transit.store.ts` 的 `fetchFavorites` 报告服务端到底答没答，索引行据此分别说「已关注 0 条」与「未读到」。**「未读到」不是在两者之间新造区分** —— 它就是这一行该报的事实：把没读到的列表渲染成「0 条」才是替使用者编了一个数字。这条与下一句的「读不到就是读不到」是同一条规则）
- **读不到就是读不到**：`GET /api/transit/settings` 失败时，锚点行与时段行给「未读到」这个事实，不给「未设置」，也不给默认时刻。这与**第三个事实**并列而不重叠：接口明确答「这个用户没有配置」时是**未设置**，既不是「未读到」也不是一组值 —— 两种形状对使用者是同一个事实、对代码是两个状态：**没存过行**（`settingsState: 'unset'` 且 `data: null`）与 **存过行但四列全空**（行在、时刻为 NULL）。消费者若忽略这个状态，拿到的是一行空值，而不是一套看起来像真的时刻。今天的折叠态摘要在读取失败时保留默认值（`index.vue` 的 `savedHours` 初值与 `catch`），索引行不继承这一点。口径与既有两处一致：F1 参考行在无结论时整行不渲染（`views/overview/reference-line.ts`），F10 空态对读不到的锚点状态既不说已保存也不说未保存（`views/commute-chain/empty-state.ts`）

**深链接**：四个子页面都是真实路径 —— `/settings/lines`、`/settings/schedule`、`/settings/anchors`、`/settings/chains`。刷新、收藏、浏览器后退都必须落在同一页；子页面不得依赖「从索引页带过来的状态」才有内容。

**每个设置子页面都带应用内的返回入口**：一个「返回设置」控件指向 `/settings`，不依赖系统手势，也不依赖浏览器后退键。

**导航模型（已定）：只有返回 —— 不做常驻 Tab 条，不做桌面侧边栏。** 理由：域只有四个，且极少来回切换；常驻导航占的是移动端最紧张的那部分屏幕，换来的收益接近零。四个域各自独立成页，返回足以表达「我在哪、怎么出去」。

**宽度**：索引页内容居中 `max-w-2xl`，子页面居中 `max-w-3xl`。今天的 `mx-auto max-w-6xl` 与 xl 双栏（`xl:grid-cols-[minmax(0,1fr)_20rem]`）随侧栏一起去掉。

**无障碍**：

- 索引是一个**列表**，每行是一个链接，该行的摘要文本在链接**内部** —— 行与它的状态不能各说一半
- 每个子页面有真正的 `<h2>`，卡片标题仍是 `<h3>`
- **可见文案必须被包含在可访问名字里（WCAG 2.5.3 Label in Name，Level A）**：名字是语音控制用户念出的词所匹配的对象，一个整体替换掉可见文案的名字会让控件「念不出来」。新 chrome 里「返回设置」这类控件如果只给 `aria-label="返回"`（或任何不含可见文案的说法）就是同一个缺陷。已落地的先例是 `views/settings/components/chain-leg-fields.vue` 的「删除该段」：名字把可见文案放在最前（`删除该段（第 1 段）`），位置或原因只作括注
- 触控目标 ≥44px（沿用既有 `min-h-11` / `min-h-[44px]` 写法）

**已知未决（不在本次改造范围内）**：链路录入的半成品草稿只活在组件内存里（`views/settings/chain-draft.ts`，草稿无持久化）。改造后从 `/settings/chains` 返回会卸载该页，**未保存的草稿会静默丢失**。本次是纯结构搬移，所以**不加导航守卫** —— 仓库现在没有任何 `onBeforeRouteLeave`，也没有 `keep-alive`。这是**未决问题，不是已定的取舍**：要保住草稿，代价是为这一个页面引入路由守卫（离开前询问，或把草稿持久化到 `sessionStorage` / store），并定义「返回时保留到哪一步」的语义；改动落地后按实际使用再定。

## 5. 核心算法与数据处理机制

### 5.1 航位推算平滑插值

上游拉取频率为 15~30 秒，前端必须消除车辆瞬移：

1. **运动估算**：上游单车数据含 `currentOrder`（当前/刚过站序）、`speed`（米/秒）、`distanceToWaitStn`（距目标站米数）。帧循环（`requestAnimationFrame`）中按 $Distance(t) = Distance(0) + \int speed \, dt$ 线性更新车辆沿拓扑轨迹（含直线与折返圆弧）的几何位置；若推算已接近下一站进站位，自动缓动减速停靠，杜绝网络延迟导致的虚假「越站」跑偏
2. **快照矫正**：新快照到达后比对推算位置与最新位置，偏差在 500ms 内以 Cubic-Bezier 缓动修正对齐

**运动契约**：绝不瞬移，绝不倒推车辆位置。

**到站分钟不使用这套推算**：运动契约只服务画面平滑。上游未给某站的到站秒数时，行**不给分钟**（按 F1.4 的零假数据：缺位就说缺位），因为拿瞬时速度外推跨多站的误差没有固定符号 —— 实测同一条公式在一条短程密集站线上偏早 5–10 分钟、在一条长环线上偏晚最多 28 分钟。可以给的是它**能**说的事实：还有几站。

### 5.2 通勤情境自适应

- 使用者配置「家」与「公司」两个位置锚点（F2）
- **时间与位置判定**：
  - 早高峰时段 → 判定为上班方向，自动筛选开往工作地的路线，目标站高亮为公司站
  - 晚高峰时段 → 判定为下班方向，自动筛选返程路线，目标站高亮为家附近站
  - 其他时段 → 按当前 mode 对应的锚点处理，**不引入运行期定位**
- 早晚高峰的起止时刻**可在设置页配置**，持久化在 `user_settings`。**没有可读的内置默认值**（`004` 曾给这四列 `NOT NULL DEFAULT`，`009` 已改回可空）：**没存过行** 与 **存过行但从没选过时段** 都是「未设置」，读接口一律如实报，绝不回一组像样的时刻；引擎内部需要一段可用区间时，用一个显式命名的内部参数承接（与地铁引擎的服务窗口同一模式）
- **允许上下班同方向**：出现该情况时给中性提示（`slate-400` + Info 图标），绝不用警告色
- **一条线路只有一条关注记录**：早晚方向、上下车点都挂在同一行上；重复关注（含反方向）按「已关注」处理（409），不生成第二张卡片

### 5.3 地铁时刻表推演引擎

基于「地铁无公开实时列车位置 API」的现状：

1. **双排班表管理**：严格分离工作日表（`workday`）与双休日表（`weekend`）。**核心规则**：法定调休补班的周六日，依然强制执行双休日时刻表（依城市地铁按周末客流排班的惯例）。**法定假日不走专用班表**（具名限制，见 §3）：假日当天按当天星期几取表
2. **虚拟区间列车推演**：依据两端始发站与关键节点发车时刻表，结合站间平均运行时长（2~3 分钟/区间），推导当前时刻整条线路上正在区间运行的列车虚拟位置，并标记「时刻表推算车」。因此地铁数据一律按 F4 标记为**排班推演**，不得渲染成实时
3. **运营日模型**：日界不是 00:00。定义 `operatingDateOf(now) = now - 4h`；`operatingDaySeconds` 把 hour < 4 的次日凌晨尾班 +24h，使时间轴连续到 `00:00~28:00`。**收班后与首班前一律返回空**，界面按 F3 显示运营状态——绝不拿次日首班车充当「即将到站」

### 5.4 坐标系统与唯一换算边界

浏览器上报的 `navigator.geolocation` 原始定位是 `WGS-84`，本系统在**唯一一处**把它换算成 `GCJ-02`：`apps/server/src/app.ts` 的 `deviceFixToGcj02`，且只换算这一次。

- **换算边界之外不再存在 `WGS-84`**：锚点与站点坐标的落库值、下发给前端与 GIS 服务的值，一律是 `GCJ-02`
- 站点坐标来自高德静态站序，**本身就是 `GCJ-02`**，必须原样转发，**不得二次换算**（二次换算会把步行终点偏移约 500 m）
- GIS 服务（`AmapGisService`）只接受 `GCJ-02`，自身不做任何换算

## 6. 数据源架构与服务容灾

### 6.1 适配器体系设计

通过策略模式与责任链解耦上游数据源变更风险：

```
                    ┌─────────────────────────┐
                    │      WebSocket / REST   │
                    └────────────▲────────────┘
                                 │ 标准 DTO
                    ┌────────────┴────────────┐
                    │  Transit Aggregator     │ (服务端统一缓存 15-20s, 上游异常自动降级)
                    └────────────▲────────────┘
                                 │
     ┌───────────────────────────┼───────────────────────────┐
     │                           │                           │
┌────┴───────────────┐  ┌────────┴──────────────┐  ┌─────────┴─────────────┐
│  ChelaileAdapter   │  │   ApiZeroAdapter      │  │ SubwayScheduleEngine  │
│  (主源 · 秒级)      │  │   (兜底 · 分钟级)     │  │ (时刻表推演模型)       │
└────────────────────┘  └───────────────────────┘  └───────────────────────┘
```

1. **统一接口定义（`packages/transit-adapter`）**：`searchLine` / `getLineDetail` / `getLiveBuses`，返回标准化 DTO
2. **主备自动降级**：优先通过 `lineId` 查询在途车，规避部分城市不支持站点反查的限制；主源连续异常时自动降级为备用热备源，并通过终点站名校准 `direction` 语义翻转问题。`isDegraded` 由**作答的那个数据源自己声明**（不是由它在 provider 数组里的位置推断）：充当替身的数据源必须自己声明 `true`，而某个 id 只有它能答时（例如地铁引擎之于 `subway_*`，chelaile 对这类 id 直接拒绝）它声明 `false` 就是正确的主答案。降级时数据包携带 `isDegraded: true`，前端按 F4 提示
3. **线路分派**：地铁线路 id 走通用地铁时刻表引擎，公交线路 id 走实时数据源
4. **边界即契约**：上游没有这条线路的记录 → **404**，绝不用「200 + 空数据」伪装成「线路存在但此刻没车」（真实线路但确实没车仍必须是 200 + 空，这一条要有正对照）；畸形查询参数（`direction` / `order` / `count`）→ **400** 并说明接受的取值，绝不静默归一化或忽略 —— 一个被静默丢掉的参数会让回答看起来是「空」而不是「你的请求不合法」

### 6.2 共享缓存与连接复用

- **严禁客户端直连第三方交通数据源**
- 服务端设立基于内存的高频短效缓存（TTL 15~20 秒）
- **WebSocket 频道广播模型**：多客户端同时查看同一线路时，服务端仅由单一定时器向上游拉取，再多播下发给订阅房间，避免触发上游风控。无客户端监听时自动暂停拉取
- **静态数据长缓存**：线路站序等静态数据是长效缓存（进程内 Map，TTL 24h）。瞬时失败**绝不覆盖已有好数据**

## 8. 数据库模型（PostgreSQL 18）

迁移为文件式 SQL（`migrations/001~008`），按序应用。**一条线路只关注一次**（`008` 迁移）：`user_favorite_lines` 上建立 `(user_id, city_code, line_id)` 唯一索引 `uniq_favorite_per_user_city_line` —— 两个方向是**同一个关注**，不是两行（方向由 `preferred_direction` / `morning_direction` / `evening_direction` 与 `reverse_line_id` 承载）；同名线路落在不同城市是不同线路，索引三列即判据。迁移遇到既有重复行**大声失败**并列出冲突键，不做静默合并（挑哪一行幸存无法从数据推导）。当前实际表：

```sql
-- 1. 用户关注线路（线路 + 通勤目的站 + 双向）
CREATE TABLE user_favorite_lines (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id VARCHAR(64) NOT NULL DEFAULT 'default_user',
    city_code VARCHAR(16) NOT NULL DEFAULT '027',
    line_id VARCHAR(64) NOT NULL,
    line_name VARCHAR(64) NOT NULL,
    preferred_direction INT NOT NULL DEFAULT 0,
    reverse_line_id VARCHAR(64),                        -- 反向线路 id（公交方向不同 id 不同）
    pinned_station_name VARCHAR(64),                    -- 本方向上车点
    reverse_pinned_station_name VARCHAR(64),            -- 反方向上车点
    morning_direction INT,                              -- 上下班各自的方向
    evening_direction INT,
    display_order INT NOT NULL DEFAULT 0,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 一条线路只关注一次：两个方向是同一个关注，不是两行
CREATE UNIQUE INDEX uniq_favorite_per_user_city_line
    ON user_favorite_lines (user_id, city_code, line_id);

-- 2. 用户设置（通勤时段）
CREATE TABLE user_settings (
    user_id VARCHAR(64) PRIMARY KEY DEFAULT 'default_user',
    morning_start TIME,                                 -- NULL = 从没选过（009 已移除 NOT NULL/DEFAULT）
    morning_end   TIME,
    evening_start TIME,
    evening_end   TIME,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 3. 静态线路与站点元数据缓存（避免高频重复拉取站名与坐标）
CREATE TABLE cached_transit_lines (
    line_id VARCHAR(64) PRIMARY KEY,
    city_code VARCHAR(16) NOT NULL DEFAULT '027',
    line_name VARCHAR(64) NOT NULL,
    direction INT NOT NULL,
    start_stop_name VARCHAR(64) NOT NULL,
    end_stop_name VARCHAR(64) NOT NULL,
    stops_json JSONB NOT NULL,
    last_fetched_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

**已就绪**（`006` 迁移）：位置锚点用 `user_settings` 的 `home_lng / home_lat / work_lng / work_lat` 四列（`DOUBLE PRECISION`，可空）；置顶用 `user_favorite_lines.is_pinned BOOLEAN NOT NULL DEFAULT FALSE`，查询排序为 `ORDER BY is_pinned DESC, display_order ASC, created_at ASC`。

更新通道也已就绪：`UpdateFavoriteSchema` 接受 `displayOrder` 与 `isPinned`，`PATCH /api/transit/favorites/:id` 据此落库；设置页的拖动排序与首页置顶都走它。

**换乘链路表**（`007` 迁移）：新增 `commute_chains`（`origin_anchor` ∈ {home, work}、`purpose` ∈ {morning, evening}，带 `display_order`）与 `commute_chain_legs`（链路的乘车段）。

**方向语义**：一条线路的两个方向是两个不同的 lineId（公交），必须分别存储；上车点与方向**按通勤目的（morning / evening）分别绑定**。

## 9. 需求依据

### 业界对标结论

- **「打开即结论」不是懒，是 Web 技术现实下的最优解**：锁屏、小组件、后台到站围栏全部要求原生能力，纯 Web 都做不到。主动触达这条路在 Web 上本来就走不通。
- **数据可信度可视化是行业成熟做法**：Transit 官方用「脉冲波纹 = 实时 / 灰显 = 按时刻表 / Cancelled」区分可信度，与零假数据约束天然一致。
- **Web 端实时公交是大厂主动放弃的空白**：高德官方 FAQ 明确「PC 端的公交线路详情页主要展示静态信息……不提供公交车实时位置追踪，建议使用手机端 App」。
- **大厂的通勤模型本项目已有**：Citymapper 的 SmartCommute 按位置 + 时间自动切换通勤方向；本项目已实现通勤时段自动切换早晚方向 + 上车点绑定。

## 11. 仓库数据卫生（重要约定）

本仓库是**公开** GitHub 仓库，已提交内容对全网可见，且 git 历史会保留旧版本。

因此 **`docs/`、测试夹具、以及任何文档中的示例，都不得使用维护者真实的通勤数据**：家庭/工作地点名称或坐标、真实关注线路与上下车点的**组合**、通勤时段。一律使用中性的合成占位符。

注意：**敏感的是「组合」，不是单个 token**。单个公交线路号与站名都是公开交通数据；私密的是描述真实路线的那一**组**——它一旦和目的地放在一起就变得可识别。因此逐 token 审查会放过不该放过的东西。
